# Y306 MCU Firmware & OTA Manual (trigger output)

> Target: Y306 carrier board (STM32F103 MCU) + Orin NX, L4T R39.2.1
> Firmware: **V1.2.10** — both ACC / NOACC variants are pre-built here, A and B slots each.

---

## 1. What the MCU does

The camera sync trigger on Y306 is generated by the on-board STM32F103:

- **Factory default 30 Hz / 10 %** (preset 3, meant for 1920×1080@30 fps sensors)
- **Not persistent**: every power-up returns to the default preset, so the rate must be sent again at boot
- Talks to the Orin over its USART1↔USB bridge (`/dev/ttyACM0`, 115200 8N1)

> ⚠️ **Firmware older than V1.2_10 (e.g. V1.0) does not implement the `0xAA` rate command
> and never outputs a trigger.** The symptom is "camera is in hardware-trigger mode but
> delivers no frames, `/dev/y306_fsync` shows zero edges". Check the version first (§3).

## 2. Firmware files and variants

```
mcu/firmware/
├── F306_MCU_A_ACC_V1.2.10.hex      with ACC/IGN power sequencing
├── F306_MCU_B_ACC_V1.2.10.hex
├── F306_MCU_A_NOACC_V1.2.10.hex    without ACC control (current Y306 configuration)
└── F306_MCU_B_NOACC_V1.2.10.hex
```

| Variant | Use | How to tell |
|---|---|---|
| **NOACC** | no ACC/IGN power sequencing (all current Y306 units) | `MCU_VER?` → `..._NOACC_...` |
| **ACC** | SoM power controlled by the IGN signal | `MCU_VER?` → `..._ACC_...` |

**A/B are the two slots** (bootloader + two 16 KB application slots); a slot that fails
CRC falls back to the other one. An OTA only writes the **inactive** slot, hence two passes.

> 🔴 **Both slots must carry the same variant.** Mixing (A=ACC, B=NOACC) changes power
> sequencing behaviour whenever the bootloader falls back. Switch variants by flashing
> both slots with two passes and two power cycles.

## 3. Check the current version (always do this first)

```bash
sudo bash mcu/upgrade.sh --variant noacc --check
# MCU_VER: F306_MCU_A_NOACC_V1.2_10
```

or directly:

```bash
sudo python3 mcu/tools/mcu_ver.py --port /dev/ttyACM0
```

> ⚠️ **Opening the serial port resets the MCU through DTR; wait 1.6 s before sending**
> or you will never get an answer. `mcu_ver.py` / `mcu_freq.py` already do this and retry.

## 4. OTA upgrade (two passes + two full power cycles)

```bash
# pass 1 — writes the inactive slot
sudo bash mcu/upgrade.sh --variant noacc

# —— FULL POWER CYCLE: switch the 12 V off, wait 5 s, power on ——

# pass 2 — writes the other slot
sudo bash mcu/upgrade.sh --variant noacc

# —— FULL POWER CYCLE again ——

sudo bash mcu/upgrade.sh --variant noacc --check
```

The script drives `tools/ota_send.py`:

1. handshake `OTA:START:F306OTA`, MCU answers `OTA:READY:<active>:<target>:16384`
2. `OTA:SIZE` → `OTA:ERASE` → 16 × 1 KB blocks (CRC16, automatic NAK retry) → `OTA:FINAL` (whole-image CRC32)
3. `OTA:OK` means the image landed in the inactive slot

### Why a full power cycle is mandatory

- The slot switch happens when the **MCU resets**, decided by the bootloader.
- **A SoM `reboot` does not reset the MCU** (the MCU is powered from the carrier's 12 V and
  keeps running while the SoM reboots) — verified: three SoM reboots kept the old version.
- A DTR pulse does not reset it either (the bridge's DTR is not wired to NRST).

### What happens if you only do one pass

You end up with "new firmware active + old firmware as fallback". If the new slot ever
fails CRC the bootloader silently rolls back — the unit quietly behaves like before.

## 5. Trigger output: rate and duty

### 5.1 Using the tool (recommended)

```bash
sudo python3 mcu/tools/mcu_freq.py 10 10      # 10 Hz / 10 %
# TX aa0103e80aa055
# RX aa02000a0ac055                          ← status 0x00 = OK, echo 10 Hz / 10 %
```

Arguments: `freq_hz` (1–655), `duty_pct` (1–100).
**Keep the duty at 10 %** — 50 % interferes with CSI capture.

### 5.2 Presets (command `0x05`, all 10 % duty)

| index | rate | note |
|---|---|---|
| 0 | 10 Hz | usual choice with 30 fps sensors |
| 1 | 20 Hz | |
| 2 | 25 Hz | |
| 3 | **30 Hz** | **factory default** (1920×1080@30 fps) |
| 4 | 60 Hz | |

> The trigger rate must be **≤ stream frame rate / 2** (30 fps stream → ≤15 Hz),
> otherwise the camera will not produce the expected frame rate.

### 5.3 Protocol reference (`0xAA` frame)

```
host → MCU : AA CMD P1 P2 P3 CS 55        CS = low byte of the sum of the first 5 bytes
MCU → host : AA 02 ST FREQ DUTY CS 55     ST: 00=OK, 01=bad parameter, 02=unsupported
```

| CMD | Function | P1P2P3 |
|---|---|---|
| `0x01` | set rate / duty | P1P2 = rate × 100 (big endian), P3 = duty % |
| `0x02` | status | returns PPS lock / watchdog state |
| `0x05` | preset | P1 = preset index |
| `0x07` | align | align counter to the PPS edge |
| `0x08` | clock sync | returns the MCU DWT microsecond timestamp |
| `0x09` | trigger timestamp | sequence number + timestamp of the last trigger |

Example, 10 Hz / 10 % → `AA 01 03 E8 0A A0 55`
(0x03E8 = 1000 = 10.00 Hz × 100; checksum = 0xAA+0x01+0x03+0xE8+0x0A = 0x1A0 → 0xA0)

## 6. Acceptance

```bash
# 1) version
sudo bash mcu/upgrade.sh --variant noacc --check

# 2) trigger edges (HTE on the SoC)
sudo y306_fsync_read.py 3
# tsc interval ns: mean=99998737 ... -> 10.0001 Hz

# 3) camera frame rate (must follow the trigger)
sudo y306_list_cams.py --probe
# video0  RGB  ...  10.00 fps
```

Expect the edge rate within ±0.1 % of the configured rate, and the frame rate equal to
the trigger rate (or an integer divider of it).

## 7. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `MCU_VER?` no reply | sent too early after opening the port (DTR reset) | use `mcu_ver.py` (1.6 s settle built in) |
| `MCU_VER?` still no reply after 1.6 s | port busy / bridge not enumerated | `ls /dev/ttyACM*`; `fuser /dev/ttyACM0` |
| version unchanged after OTA | only the inactive slot was written, no power cycle | full power cycle (SoM reboot is not enough) |
| camera 0 frames, zero edges | MCU firmware < V1.2_10, no trigger generated | upgrade per §4 |
| frame rate is half the trigger rate | trigger > frame rate / 2 | lower the trigger rate or raise the stream rate |
| unit comes up at 30 fps instead of 10 fps | MCU default preset is 30 Hz and the service has not sent the rate yet | check `y306-orbbec-trigger.service` |
| power behaviour changed after upgrade | wrong ACC/NOACC variant | reflash the correct variant twice |

## 8. Recovery and variant switching

Switch variant (e.g. NOACC → ACC):

1. `sudo bash mcu/upgrade.sh --variant acc` → full power cycle
2. `sudo bash mcu/upgrade.sh --variant acc` → full power cycle
3. `--check` confirms both slots report `_ACC_`

> If a unit cannot boot because of a variant mismatch, connect **ST-Link +
> STM32CubeProgrammer** and flash `bootloader (0x08000000)` + `slot A app (0x08004000)`
> directly, bypassing OTA.
